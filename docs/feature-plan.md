# 游戏厅扩展需求与架构方案

## 产品需求拆解

### 1. 历史成绩

- 在首页提供明确入口，并增加独立成绩页。
- 汇总数独、1024、云雀跃、暮色拾星、迷宫和单词寻踪的每局结果。
- 展示总局数、完成局数、最近游玩时间、游戏/难度筛选和各游戏最佳表现。
- 数据仅保存在当前设备；支持用户主动清空，并在操作前二次确认。

### 2. 游戏工具：骰子

- 工具与正式游戏分区展示，避免成绩和工具使用记录混淆。
- 支持 1–6 枚骰子以及 D6、D8、D10、D12、D20。
- 展示每枚结果、点数总和及最近五次结果；提供掷骰动画和无障碍播报。

### 3. 迷宫

- 简单、中等、困难对应 9×9、15×15、21×21 三种迷宫。
- 每局生成可解且只有一条主路径的随机迷宫。
- 支持键盘方向键、WASD、屏幕方向按钮和滑动。
- 展示用时、步数、最佳路线步数；完成后写入历史成绩。

### 4. Crossword / 单词寻踪

- 采用“在字母网格中寻找交叉隐藏单词”的玩法，兼顾移动端操作。
- 简单、中等、困难对应不同词汇长度、数量和网格尺寸。
- 待找词始终展示中文意思；点击词卡展示简单英文例句。
- 支持横、竖、斜向及倒序选词；完成后写入历史成绩。

## 具体工程任务

1. 建立统一的本地成绩数据结构与读写函数。
2. 新增成绩页及筛选、统计、清空能力。
3. 为现有四款游戏接入成绩写入。
4. 新增骰子工具路由、交互状态与首页工具区。
5. 新增迷宫生成算法、操控、计时、难度与完成逻辑。
6. 新增词库、随机棋盘生成、拖拽选词、词义例句与难度逻辑。
7. 更新首页信息架构、SEO、站点地图、PWA 离线缓存和自动化测试。
8. 完成响应式、键盘操作、触控操作、屏幕阅读器标签和构建验证。

## 架构设计

- 继续使用现有 Next/Vinext 路由架构；每个游戏保持独立页面，减少彼此状态耦合。
- `app/lib/score-history.ts` 作为统一成绩边界，使用带版本号的 localStorage key，
  记录标准化的游戏、难度、分数、用时、步数、错误数及时间戳。
- 迷宫和单词棋盘均在客户端按难度生成，不依赖网络，确保 PWA 离线可玩。
- 不引入数据库：成绩属于设备本地个人数据，符合当前项目的隐私承诺。
- service worker 预缓存新增路由，首页 manifest 继续覆盖工具和新增游戏。
- 用静态路由渲染测试覆盖新增入口与元数据，用构建/类型检查验证算法与组件。

## 全局决策：移动端游戏页信息层级

- 手机/窄屏沿用各页面现有堆叠断点，导航收紧后优先展示可操作的核心游戏区（playfield-first）。
- 顶部展示性大标题在手机端隐藏；难度、模式、重新开始、批量打印、说明等次要内容统一置于游戏区之后。
- 计时、分数、生命、暂停等进行中必需状态随游戏区保留；游戏 overlay 内的恢复/重玩动作可继续保留。
- 移动端交互控件提供约 44px 触控目标，底部内容预留 `safe-area-inset-bottom`，并避免横向溢出。
- 桌面端 DOM 顺序与视觉布局保持不变。
- 覆盖路由：`/sudoku`、`/1024`、`/sky-hop`、`/twilight-canopy`、`/maze`、`/crossword`、`/hanzi-listen`、`/tools/dice`。
